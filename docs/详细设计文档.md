## 1. System Overview

### 1.1 Project Scope

A full-cycle general-purpose ERP（企业资源计划系统）— covering 商品（Item+SKU）主数据、库存、采购、销售、制造质检、财务、人力资源、项目、固定资产、审批流、通知与门户。后端 crate 名为 `erp-server`，数据库为 SQLite3（`sqlite://data/erp.db?mode=rwc`）。

### 1.2 Core Capabilities

| Capability | Description |
| ----------- | ------------- |
| 商品全生命周期管理 | 从采购收货入库到销售发货出库的完整追溯 |
| 进销存一体化 | 采购、库存、销售全链路联动 |
| 制造与质检 | BOM、工单、质检（Inspection）、不合格品单（NCR）闭环 |
| 审批流 | 单据审批流转引擎（定义/实例/任务） |
| 多用户 RBAC | 角色/权限/部门/租户（4 个示例角色：admin/warehouse/sales/procurement） |
| 人力资源与财务 | 员工/考勤/薪资/劳动合同；科目/日记账/发票/付款/试算平衡 |
| 项目与固定资产 | 项目/WBS/预算；登记/直线法折旧/处置 |
| 通知与门户 | 通知收件箱/模板/偏好；门户账户（Party） |
| 国际化 | 中英文 UI + 商品单位换算 |

## 2. Tech Stack Decisions

### 2.1 Backend Technology

| Layer | Choice | Version | Rationale |
| ------- | -------- | --------- | ----------- |
| **Web Framework** | Axum | 0.8+ | 最主流的 Rust 异步 Web 框架，Tower 中间件生态，社区活跃 |
| **ORM / SQL** | SQLx | 0.8+ | 编译期 SQL 检查，非侵入，`sqlite` feature 原生支持 SQLite3 |
| **Database** | SQLite3（WAL 模式） | 3.46+ | 零配置、单文件数据库；连接串 `sqlite://data/erp.db?mode=rwc` |
| **Serialization** | Serde + Serde JSON | 1.x | Rust 标准序列化框架 |
| **Auth** | Axum + JWT (jsonwebtoken) | — | 无状态认证，适合前后端分离 |
| **Password Hashing** | Argon2 | — | OWASP 推荐密码哈希算法 |
| **Async Runtime** | Tokio | 1.x | Rust 异步运行时标准 |
| **Validation** | Validator | 0.19+ | derive 宏结构体校验 |
| **Logging** | Tracing + Tracing-Subscriber | — | 结构化日志，JSON 输出 |
| **File Upload** | Axum multipart + tokio-util | — | 附件上传（商品图片、单据扫描件等） |
| **Export/Import** | calamine (read) + rust_xlsxwriter (write) | — | Excel 读写 |
| **API Docs** | utoipa + utoipa-swagger-ui | — | OpenAPI 3.0 自动生成文档 |

### 2.2 Frontend Technology

The frontend is a React 19 SPA with the following architecture:

| Layer | Choice | Notes |
| ------- | -------- | ------- |
| **UI Framework** | React 19 | Latest stable |
| **Routing** | react-router-dom v7 | createBrowserRouter with protected routes |
| **Client State** | Zustand 5 | Auth store, app store, unit conversion store |
| **Server State** | TanStack Query 5 | 2-min staleTime, 5-min gcTime, retry: 1 |
| **UI Component Library** | Ant Design 5 | Enterprise-grade, great for admin dashboards |
| **Internationalization** | react-i18next | Per-feature namespaces, zh-CN primary + en |
| **HTTP Client** | Axios | Instance at `/api/v1`, auto Bearer token |
| **Validation** | Zod 3 | Runtime response validation via `validateResponse.ts` |
| **Type Safety** | TypeScript 5 | Strict mode, noUnusedLocals, noUnusedParameters enforced |
| **Build** | Vite 6 | Dev proxy `/api/*` → `localhost:3000` |

**Feature modules**: auth, items, inventory, suppliers, customers, purchases, sales, workflow, hr, finance, procurement, manufacturing, projects, assets, notifications, portal, contracts, reports, search, profile. Each feature has `api/`, `pages/`, `types/` subdirectories plus `queryKeys.ts`.

### 2.3 Architecture Style

**RESTful 前后端分离**：后端提供 JSON REST API，前端通过 HTTP 消费。

**模块化单体（modular monolith）**：鉴于项目规模与团队规模，采用模块化单体，内部按领域分层。

## 5. Database Design

### 5.1 Design Principles

- **SQLite3 WAL 模式**：连接串 `sqlite://data/erp.db?mode=rwc`，通过 `PRAGMA journal_mode=WAL;` 启用读写并发
- **无外键约束**：SQLite 外键性能开销明显；引用完整性在应用层保证
- **索引策略**：高频查询字段建索引；组合查询建复合索引
- **时间戳格式**：ISO 8601 文本格式（`TEXT`）
- **枚举字段**：以 `TEXT` 存储，可读且可扩展
- **软删除**：关键表含 `deleted_at` 列，不做物理删除
- **迁移策略**：37 个历史迁移文件重写为 SQLite 语法，删除管材/标签/质证书等钢管时代遗留模块相关表，新增通用商品表与各业务模块表

### 5.2 Database Initialization

```sql
-- Enable WAL mode
PRAGMA journal_mode = WAL;
-- Enable foreign keys (app-layer control, but keep validation on)
PRAGMA foreign_keys = ON;
-- Set busy timeout
PRAGMA busy_timeout = 5000;
-- Sync mode: NORMAL balances performance and safety
PRAGMA synchronous = NORMAL;
-- Cache size: 64MB
PRAGMA cache_size = -64000;
-- Temp storage: memory
PRAGMA temp_store = MEMORY;
```

## 6. REST API Design

### 6.1 API Base Convention

**Base path**: `/api/v1`

**统一响应格式**（ApiResponse<T> / PaginatedResponse<T>）：

```json
// 成功响应
{
  "success": true,
  "data": { ... },
  "meta": {
    "page": 1,
    "page_size": 20,
    "total": 100,
    "total_pages": 5
  },
  "request_id": "req_xxxxx"
}

// 错误响应
{
  "success": false,
  "code": 12001,
  "message": "商品不存在",
  "details": { "item_id": 123 },
  "request_id": "req_xxxxx"
}
```

**认证方式**: `Authorization: Bearer <jwt_token>`

**分页参数**:

| Param | Type | Default | Description |
|-------|------|---------|-------------|
| `page` | integer | 1 | 页码 |
| `page_size` | integer | 20 | 每页条数（最大 100） |

### 6.3 库存管理 API

#### 6.3.1 入库管理

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/api/v1/inbound-records` | 入库单列表（头） |
| `POST` | `/api/v1/inbound-records` | 创建入库单（头+明细一次提交）。**约束**：inbound_type='purchase' 需 order_id，系统自动校验采购订单已审批 |
| `GET` | `/api/v1/inbound-records/{id}` | 入库单详情（含明细） |

| `DELETE` | `/api/v1/inbound-records/{id}` | 删除入库单（仅 auto_approved 或 rejected 状态） |

**POST /api/v1/inbound-records request body — 采购入库**:

```json
{
  "inbound_type": "purchase",
  "inbound_date": "2026-08-01",
  "order_id": 1,
  "supplier_id": 1,
  "operator_id": 1,
  "remark": "采购入库",
  "items": [
    { "item_id": 1, "quantity": 100 },
    { "item_id": 2, "quantity": 50 }
  ]
}
```

**POST /api/v1/inbound-records request body — 非采购入库（需审批）**:

```json
{
  "inbound_type": "production",
  "inbound_date": "2026-08-01",
  "operator_id": 1,
  "remark": "生产完工入库",
  "items": [
    { "item_id": 100, "quantity": 10 }
  ]
}
```

> **Approval flow**: 当 inbound_type='production' 或 'return' 时，创建后状态为 'pending'，审批后才更新库存。
> **批量入库**: 若 `items` 为空且提供 `batch_create`，系统自动创建 N 件同规格商品并一次性入库。批量入库仅支持 inbound_type='purchase'。

| Method | Path | Description |
|--------|------|-------------|
| `POST` | `/api/v1/inbound-records/batch` | 批量创建商品 + 一步入库（仅采购类型） |

```json
// POST /api/v1/inbound-records/batch request body
{
  "inbound_type": "purchase",
  "inbound_date": "2026-08-01",
  "order_id": 1,
  "supplier_id": 1,
  "operator_id": 1,
  "remark": "批量采购入库",

}
```

## 8. Error Handling & Response Convention

### 8.1 HTTP Status Codes

| Code | Scenario |
|------|----------|
| `200` | GET / PUT success |
| `201` | POST create success |
| `204` | DELETE success (no response body) |
| `400` | Bad request (validation failure) |
| `401` | Unauthenticated (no token or expired) |
| `403` | Forbidden (role doesn't have permission) |
| `404` | Resource not found |
| `409` | Conflict (e.g. duplicate SKU) |
| `422` | Request body validation failure (Validator) |
| `500` | Internal server error |

### 8.2 Error Code Definitions

```rust
pub enum AppErrorCode {
    // General (100xx)
    InternalError,          // 10001
    ValidationError,        // 10002
    NotFound,               // 10003

    // Auth (110xx)
    Unauthorized,           // 11001
    TokenExpired,           // 11002
    Forbidden,              // 11003

    // Item/商品 (120xx)

    // Inventory (130xx)

    LocationFull,           // 13002
    LocationNotFound,       // 13003

    // Orders (140xx)
    OrderCannotModify,      // 14001 (已审批订单不可修改)
    OrderNotFound,          // 14002
```

### 8.3 Global Error Handling

所有错误经 Axum `FromRequestParts` / 中间件统一转换为 `ApiErrorResponse` 格式（`success: false` + `request_id`）。响应头通过 tower-http 传播 `x-request-id`。

## 9. Non-Functional Design

### 9.1 Performance Design

| Metric | Approach |
|--------|----------|
| **查询响应 ≤ 2s（10 万行）** | 合理索引 + 分页 + 避免 N+1 查询 |
| **导入 10 万行 ≤ 60s** | 批量插入（SQLx `execute_many`），事务分批提交（每批 1k 行） |
| **并发 20+ 用户** | SQLite WAL 模式支持读写并发；写入经 `busy_timeout` 串行化 |
| **大数据查询** | 复杂聚合走 BI 汇总表 / 应用层缓存 |

**SQLite 并发注意事项**:

```
1. 使用 WAL 模式（默认配置），读不阻塞写
2. 写操作经 Tokio Mutex 串行化，避免 SQLITE_BUSY
3. 连接池: SQLx SqlitePool，最大连接数 = 5（WAL 允许多个并发读）
4. 长时间写事务拆分为小批次
5. 周期性 PRAGMA wal_checkpoint(TRUNCATE) 控制 WAL 文件大小
6. 连接串固定: sqlite://data/erp.db?mode=rwc
```

### 11.2 Unit Switching

**策略**：商品自带「单位」字段（kg / m / pc 等）。跨单位换算（如 kg ↔ t、m ↔ km）在前端 `unitStore` 中按换算系数处理；后端存储与商品单位字段保持一致。

**API 设计**：

```json
// 商品单位随主数据返回
{
  "data": {
    "sku": "FG-202608-0001",
    "name": "成品A",
    "unit": "kg",
    "quantity": 1000
  }
}
```

**实现**：

- `items.unit` 字段定义商品计量单位
- 前端 `unitStore` 保存用户单位换算偏好（标准/公制/英制）
- 展示层按用户偏好做换算显示，不改变后端存储
- `Measurement<T>` 包装类型（DTO 层）携带单位信息，可选

## Appendix A: Architecture Decision Records (ADR)

### ADR-001: Modular Monolith over Microservices

| Item | Content |
|------|---------|
| **Context** | 中等项目规模，小团队 |
| **Decision** | 模块化单体，内部按领域封装，不拆分微服务 |
| **Rationale** | 运维复杂度低；SQLite 单库不支持分布式；未来可按模块边界拆分 |
| **Consequences** | 需严格模块边界设计，防止跨模块耦合 |

### ADR-002: SQLite 作为唯一数据库

| Item | Content |
|------|---------|
| **Context** | 数据量约数十万行，20+ 并发用户 |
| **Decision** | SQLite3（`sqlite://data/erp.db?mode=rwc`）WAL 模式 + 连接池 + 写串行化 |
| **Rationale** | 零配置、文件级部署，足以支撑该规模；37 个历史迁移重写为 SQLite 语法并删除管材表 |
| **Consequences** | 保留应用层无外键约束设计，未来如需更大规模可评估托管 SQL 方案，SQLx 兼容性好 |

### ADR-003: 单一商品表（Item）作为唯一业务实体

| Item | Content |
|------|---------|
| **Context** | 原系统按行业类型拆表（管材），字段差异大、查询需跨表合并 |
| **Decision** | 统一为单一 `items` 表：sku / name / category / unit / spec / status，无行业专属字段 |
| **Rationale** | 通用 ERP 的商品形态多样，单表 + 分类/规格更灵活；跨类型查询无需 UNION |
| **Consequences** | 行业专属校验字段删除；分类与规格成为商品的两个通用维度 |

### ADR-004: 模块删除与保留边界

| Item | Content |
|------|---------|
| **Context** | 钢管时代模块（管材/标签/质证书）不再适用 |
| **Decision** | 删除管材/标签/质证书等钢管时代遗留模块；保留并泛化库存；以「制造质检（BOM/工单/质检/NCR）」承接质量能力；新增审批流/HR/财务/项目/资产/通知/门户/BI |
| **Rationale** | 通用 ERP 需要覆盖采购、销售、库存、制造、财务、人事全链路 |
| **Consequences** | 数据导入导出、搜索、报表均改为面向通用商品/单据 |
