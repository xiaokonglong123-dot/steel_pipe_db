## 实测结果

| 目标 | 实测 |
| --- | --- |
| 登录下发会话 | `POST /api/auth/login` → 200，三个 cookie：`access_token`/`refresh_token`（httpOnly、`SameSite=Lax`、无 `Max-Age`）+ `csrf_token`（非 httpOnly） |
| 身份校验 | `GET /api/auth/me` → 200 `{user_id,username,display_name,role,token_version}` |
| 401/302 双轨（A11） | API 客户端 → `401` JSON + `WWW-Authenticate`；`Accept: text/html` → `303 Location: /login` |
| CSRF（A12） | 缺 cookie 或缺 header → `403`；cookie≠header → `403`（常量时间比较） |
| 刷新轮换（A15/A16） | 新 refresh 落库，旧 refresh → `401` |
| 登出（A14） | `POST /api/auth/logout` 清 `last_refresh_jti` 并清 cookie，旧 refresh 立即失效 |
| 限流（A17–A20） | 用户不存在也跑一次哑校验（防用户名探测）；第 10 次失败 → 1 条 `login_lockout` 审计（`user_id=NULL`）；锁定/IP 层 429 不写 |
| 用户管理 | `GET/POST /api/users`、`/{id}/active`、`/{id}/password`、`/{id}/revoke`，全部 `require_admin`；最后一个管理员不可停用/降级 |
| 引导 | `STEELPIPE_ADMIN_USERNAME/PASSWORD` → 创建或重置 admin（`bootstrap::ensure_admin`） |
| 审计链 | 锁定事件后 `verify_chunk` 通过（A22） |

## 与旧实现的刻意差异（已写入规格）

1. `jsonwebtoken` 默认 60 秒过期宽限 → 显式 `leeway = 0`。
2. 旧 `sub.parse().unwrap_or(0)` → 返回 `InvalidSubject`（旧行为是把非法 sub 当用户 0，属鉴权漏洞）。
3. 限流状态从进程内 dict → `login_attempts` 表（A23），重启不清零。
4. 用户不存在时执行哑哈希校验，对齐响应时间。
5. 登录成功仍不写审计（与旧实现一致，避免高频行污染链）。
